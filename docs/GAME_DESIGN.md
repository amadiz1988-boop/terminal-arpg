# 遊戲設計基準

## 產品定位

鬼島傳說是以 rAthena Renewal 規則與 OpenKore 自動化行為為基準的 RO 純掛機遊戲。角色在持續世界中逐格移動、索敵、戰鬥、拾取、補給、死亡、重生與成長；玩家透過職業、能力、技能、裝備、地圖與資源政策改變結果。

玩家的主要決策集中在設定與養成。rAthena 世界與 OpenKore 自動化執行角色移動、攻擊、尋路、拾取與回復，8788 Dashboard 以小地圖、狀態視窗與戰鬥終端呈現實際狀態及事件。

## 核心循環

```text
建立或選擇角色
→ 設定掛機與資源政策
→ 在 RO 格狀地圖逐格移動
→ 依視野與策略選擇目標
→ 以普攻或已核對技能交戰
→ 逐件判定掉落與拾取
→ 受 HP、SP、重量或死亡條件影響
→ 補給、存倉、販售、配點、學技能或轉職
→ 返回掛圖並繼續掛機
```

目前可直接遊玩的主要掛圖是 `prt_fild08`；城鎮、跨圖、NPC 與職業流程依來源覆蓋度逐步加入。規劃中的內容要先在 [TODO.md](TODO.md) 建立完成條件，再進入正式資料。

## 玩家與系統責任

### 系統自動執行

- 逐格尋路、索敵、普通攻擊與已啟用的技能策略。
- 怪物的巡走、攻擊、重生、死亡與掉落。
- 依玩家政策拾取、忽略、負重停止、蒼蠅翅膀與隨機巡走。
- HP／SP 自然恢復、死亡重生、Base／Job EXP 與等級提升。
- 任務或轉職流程中由 OpenKore 路線與 rAthena NPC 共同裁定的移動和對話。

### 玩家決定

- 職業志願、能力點、技能點、裝備穿脫與道具政策。
- 掛機地圖、目標、技能條件、HP／SP／重量門檻與補給策略。
- 是否停止掛機並前往 NPC、倉庫、商店、轉職或其他已接入服務。
- 後續內容中的地圖選擇、資源使用與養成路線。

Dashboard API 的玩家操作先驗證工作階段、角色擁有權、目前狀態與命令範圍，再交由 OpenKore 或 rAthena 執行。介面不能新增或改寫傷害、掉落、經驗、重量、任務或職業規則。

## 世界與事件

現行狀態包含角色、怪物、地面物品、地圖座標、HP／SP、經驗、重量、裝備、技能、任務、掛機旗標與事件。rAthena、MariaDB、OpenKore status export 與 log 提供這些資料，Dashboard 負責合併及呈現。

小地圖、基本資訊、戰鬥終端、道具與還原進度讀取同一份世界狀態。這使每個可見結果都能回到一個事件與一筆資料，避免 UI 以動畫自行結算。

## 來源優先序

規則進入正式資料前依以下順序取得證據：

1. 鎖定版 rAthena 原始碼、Renewal `db/re`、`npc` 與 `doc`。
2. 鎖定版 OpenKore 原始碼與設定行為。
3. Gravity 官方公告、官方遊戲說明與可驗證 RO 遊戲內行為。
4. 具版本、畫面與重現步驟的實機驗收。
5. 社群實測或專案推導，需明確標記並取得使用者核准。

來源、版本、原始效果、實作差異與驗證日期留在資料的 `SourceTrace` 或對應稽核文件。缺少證據時保留 `【資料不足，無法確認】`。

## 介面原則

- 以 RO Default Skin 的視窗、按鈕、資訊層級與繁體中文為基準。
- 小地圖顯示真實格線與角色／怪物位置；戰鬥終端顯示實際事件。
- 玩家可看到角色正在做什麼、為何停止、何時負重或死亡，以及下一個自動動作。
- 手機寬度是必要驗收尺寸；水平溢位、瀏覽器錯誤、素材 404 與狀態不同步都屬失敗。
- 官方素材缺件時顯示待補狀態，保留來源與缺件紀錄。

## 目前產品邊界

- 資料來源與規則限定於 RO Renewal、OpenKore、Gravity RO 及可重現的實機結果。
- 現行玩家流程以 MariaDB 保存正式伺服器資料；Vinext／D1 與 `game/ro/world/simulation.ts` 屬封存原型，不進入現行玩家流程。
- 純玩家手動移動與即時動作戰鬥不屬目前核心玩法；玩家透過設定與養成影響自動化結果。

## 驗收標準

每個新功能至少需要：

1. 固定來源與資料欄位對照。
2. 領域測試涵蓋限制條件、資源消耗、重連與重播。
3. 玩家頁在手機寬度確認狀態、事件、素材與瀏覽器錯誤。
4. 相關文件記錄完成、未完成與下一步。
5. 公開版本完成 Dashboard 全部發布門檻並保存測試、提交 SHA、部署與公開 HTTPS 證據；綜合指令建立前維持 `未通過發布門檻`。

產品品質仍以實際交戰、值得查看的掉落、可感知成長、有選擇的打造與可改變玩法的流派為長期評估軸；這些評估不因技術部署成功自動完成。
